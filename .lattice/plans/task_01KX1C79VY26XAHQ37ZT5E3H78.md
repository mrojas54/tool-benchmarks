### `ToolCall` (S4)
`@dataclass` with fields exactly: `agent, source, project, name, input_chars,
output_chars, session_id, ts, usage, duration_ms, error`. `tokens` and
`input_tokens` are derived (`@property`) as `output_chars // 4` and
`input_chars // 4` respectively — integer division per spec's `/4` read as
floor-division on char counts (matches BUILDPLAN's `chars/4` framing for
S19 context-cost tokens). No third-party imports (S20) — stdlib
`dataclasses` only. Field types: plain enough for mypy --strict (`str`,
`int`, `dict[str, object] | None` for `usage`, `float | None` for
`duration_ms`, `str | None` for `error`, `session_id: str`, `ts: str`).

### `result_len` (S3)
Signature: `result_len(payload: object) -> int`. Four shapes to handle:
1. `str` → `len(payload)`.
2. `dict` → normalize via `json.dumps` (stable char-length proxy) — NOT in
   scope to guess T2's exact resolution rules (S2); this ticket only needs a
   generic dict length rule since S2's block-local-vs-toplevel resolution
   logic belongs to `parse_session` (T2), which will call `result_len` on
   an already-resolved payload.
3. MCP block-list → `list[dict]` where each block has a `"text"` key (or
   similar) — sum the text lengths across blocks.
4. Block-local `content` payload → a dict shaped like
   `{"content": [...]}` (Anthropic tool-result content-block shape) — sum
   the nested block text the same way as (3).
This ticket's tests fabricate all four shapes directly (they do not depend
on real transcript fixtures, which are T2/S24's job).

### Tests (`tests/test_records.py`)

- `test_result_len_block_local_content` — `{"content": [{"type": "text",

- `test_toolcall_derived_tokens` — assert `tokens == output_chars // 4` and

  non-multiple-of-4 case (to nail down floor division, not round or ceil).
